# fewshot

[![CI](https://github.com/forrest-grover/fewshot/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/forrest-grover/fewshot/actions/workflows/ci.yml) [![coverage](https://img.shields.io/endpoint?url=https://raw.githubusercontent.com/forrest-grover/fewshot/badges/coverage.json)](https://github.com/forrest-grover/fewshot/actions/workflows/ci.yml)

Few-shot image classification from a handful of labeled examples per class. Images are embedded with a pretrained vision model (CLIP or DINOv2) and classified against the class examples, so there is no training run: adding, removing, or relabeling an example changes predictions immediately.

The same engine is exposed four ways: a Python library, a CLI, a REST API, and a web UI.

## Setup

```bash
conda create -p ./.env python=3.12 nodejs=22 -c conda-forge
./.env/bin/pip install --no-deps -c constraints.txt torch torchvision --index-url https://download.pytorch.org/whl/cu128   # RTX 50xx needs cu128+
./.env/bin/pip install -c constraints.txt -e ".[dev]"
cd web && npm install && npm run build && cd ..
./.env/bin/fewshot serve            # UI at http://127.0.0.1:8000, API docs at /docs
```

Data lives in `$FEWSHOT_HOME` (default `./fewshot_data`): one folder per task with its images and `task.json`, plus a shared SQLite embedding cache. The server and CLI can use the same workspace at once: each change to a task locks it, starts from the latest saved `task.json`, and replaces the file atomically (the lock needs Linux or macOS), and the cache runs in WAL mode so one process's writes don't fail the other's. `fewshot cache info` shows the cache's size per model; `fewshot cache prune` deletes vectors no task's examples use, such as those of deleted examples and `bench` datasets (with every task locked meanwhile, so an image being added can't lose its vector; the cache reuses the space, and `--vacuum` shrinks the file, which keeps other processes from writing to the cache while it runs). At most two built-in models stay loaded at once (`FEWSHOT_MAX_MODELS`); loading another unloads the least recently used. The web UI scales images down to at most 1024 px on the longest side (as JPEG) before uploading them as examples or for prediction, and sends a large drop in batches of up to 100 images (and at most 32 MB, or half the server's request size limit if that is lower), showing progress with a Cancel button; an upload keeps going while you switch tabs (and when the task is renamed), stops when you cancel it or open another task (after the batch being sent, so it is counted), and if it stops part-way the UI says how many images got in; Undo during an upload stops it and then undoes all of it, and of any other drops still being sent, but not a change made meanwhile (a relabel, say, or labelling inbox images): undoing stops there and says how much of the upload is under it (a class being uploaded to can't be renamed or deleted until its upload ends); the CLI and API store whatever they are given. In the UI you can drag thumbnails between classes, tick several (Shift+click for a range) to move or delete them together, and paste images: on the Examples tab into the class under the pointer, on the Predict tab to classify them. Number keys 1–9 move ticked examples to that class, or add the highlighted prediction as that class (Enter accepts the prediction). Prediction and evaluation results stay while you switch tabs. The home page is a dashboard of all tasks: size, inbox, the last evaluation's accuracy (marked * when the task changed since) and warnings such as classes with too few examples or strong imbalance; `fewshot list` shows the same. On the Examples tab you can search file names, tags and notes, sort, and collapse classes; clicking a thumbnail opens it full size, where ←/→ step through the class, 1–9 move the example and Delete removes it. Press ? for every keyboard shortcut. A task can be duplicated (Settings, `fewshot copy`, `POST .../duplicate`), with or without its examples, to try other settings safely. For UI development, run `fewshot serve` and `npm run dev` in `web/`; Vite proxies `/api` to port 8000. `npm test` runs the UI's unit tests, and after changing the API, `npm run gen:api` regenerates the UI's types from its OpenAPI schema (`npm run check:api` checks they are current).

Every change to a task can be undone (`fewshot undo`, the Undo button or Ctrl+Z in the UI, `POST .../undo`) and redone until the next change (`fewshot redo`, Ctrl+Shift+Z, `POST .../redo`); each step is labelled, e.g. "delete 3 examples". The last 20 versions of `task.json` are kept in the task's `history/` folder, and a deleted example's image stays until no kept version names it, and `cache prune` keeps the vectors of images undo or redo may bring back. A damaged `cache.sqlite` is moved aside and a new cache started. Images are stored once per workspace, in `blobs/`, and hard-linked into each task that uses them; `fewshot cache prune` also removes stored images no task uses, and `fewshot gc` cleans up after crashes: half-made or half-deleted task folders, image files no version of their task uses, and unused stored images. Creating, duplicating, importing and deleting a task move whole folders into place (a duplicate hard-links the source's images rather than copying them), so a crash never leaves half a task, and a task whose folder was renamed (by hand, or by a rename that was interrupted) opens under the folder's name. One undo takes back a whole upload or import, however large (a drop of more than 100 images in the UI is sent as several uploads with the same `undo_group` form field, which makes them one undo step too, as are drops to several classes sent at the same time; a task's `undo_group` field says which group the next undo step belongs to). Exports lock the task while they run (a shared lock, so they and `cache prune --dry-run` work in a workspace you can only read). Examples can carry tags and a note (`fewshot example tag/note`, or in the UI the ✎ button on a thumbnail, or tick several and "Tag…", which open a small editor with suggestions from the task's tags), and the Examples tab can show only one tag. After an undo or redo the UI says what it was and offers the reverse. On a phone, the task list folds into a menu. A task can be renamed, and exported as a zip of its settings, labels and images and imported into another workspace (`fewshot export` / `fewshot import-task`, or Settings → Export and New task → Import).

Models run on CUDA if available, then Apple's GPU (MPS), then the CPU; `FEWSHOT_DEVICE` (e.g. `cpu`, `cuda:1`), or the CLI's `--device`, picks one. If the GPU runs out of memory, the batch is split in halves; later batches stay smaller until 20 have fitted, then grow back. A model is never unloaded to make room for another while an operation that uses it (embedding, predicting, evaluating) is still running, even between batches. The SigLIP 2 preset needs `transformers` for its tokenizer (`pip install -e ".[siglip]"`).

## Inbox: labelling with the model's help

Each task has an inbox for images that aren't labelled yet (the Inbox tab, `fewshot inbox add TASK dir/`, `POST .../inbox`). The model suggests a class for each, and the inbox can be ordered so that the images it is least sure about come first (labelling those teaches it the most), the most confident come first (to accept them in bulk), or the least familiar come first (new kinds of image). On the Inbox tab, Enter accepts the highlighted suggestion, 1–9 label it as that class and Delete dismisses it; "Accept N suggestions" labels everything above a confidence. From the command line: `fewshot inbox ls TASK --sort uncertain`, `fewshot inbox accept TASK --min-confidence 0.9`, `fewshot inbox accept TASK ID... --label cat`, `fewshot inbox dismiss TASK ID...`. Labelling moves images to the examples; every step can be undone, and the inbox is part of exports.

## How classification works

Each task has an embedder, a classifier, and classes. A class has example images, an optional text description, or both.

| Classifier | Image score |
|---|---|
| `gda` (default) | Gaussian discriminant analysis: class means (pulled towards their descriptions) with a shared covariance shrunk towards a sphere, on centred features; its weight against the text and its confidence scale are fitted per task |
| `prototype` | cosine similarity to the class's mean embedding |
| `knn` | similarity-weighted vote of the k nearest examples |
| `logreg` | logistic regression trained on the examples |

`gda` shrinks its covariance by D/(D + dof) (D: embedding size, dof: images minus classes), so with one image per class it is a nearest-mean classifier and with many it uses how each class actually spreads. With descriptions, each class's mean is also pulled towards its description moved across the modality gap, as if the description were λ more images: a few images are a noisy estimate of where a class lies, and the description a biased but steady one. λ is set per task by empirical Bayes (1.5 × σ²/τ², from how far the images spread around their class means and how far the means sit from their descriptions; after DEFTS, arXiv 2611.21993), so it is large when images are few or scattered and fades as they accumulate. The pull is skipped when the descriptions don't pick out their own classes' images (each class's mean must be nearest its own description more often than chance, by a one-sided binomial test at p < 0.05; with fewer than 4 described classes, where that test can't pass, the descriptions must instead classify the example images better than chance, which on pairs of classes adds 0.3 points at 4 images per class): with shuffled descriptions it would cut held-out accuracy at 2 images per class from 28.6% to 22.6% with PE Core B/16, and from 45.5% to 22.2% with PE Core L/14. On the held-out datasets this adds 0.5/1.1/0.9/0.5/0.1 points at 1/2/4/8/16 images per class with PE Core B/16 (0.2/0.8/0.6/0.4/0.2 with PE Core L/14), and makes confidence better calibrated on average, mostly at 2 images per class; image-only tasks are unchanged. The image term's weight against `100 × cos` is then chosen by leave-one-out cross-entropy on the examples, pulled towards 0.2·k^0.6 for k images per class (fully at k = 1, less as k grows), since how much to trust the images over the text differs a lot between tasks: flowers want five times the weight pets do; `text_weight` multiplies the text's share on top of that, in the scores and in the means' pull towards the descriptions (1 keeps the tuned balance, 2 doubles the text's weight, and values near 0 fit almost as without text). A last scale, fitted the same way with each example also taken out of the covariance, makes confidence match accuracy. Over six datasets (Pets, DTD and Flowers to develop it; Aircraft, EuroSAT and Food-101 held out) with CLIP ViT-B/32 and SigLIP 2, it beats `prototype` at every shot count; on the held-out datasets with descriptions, 1/2/4/8/16 shots go from 61.6/64.7/66.8/67.7/68.2% to 61.6/65.7/70.6/75.1/78.1%, and image-only from 45.1/55.0/63.6/68.9/71.7% to 46.6/58.4/67.5/73.8/77.6% (all classes of each dataset at once, 3 seeds). Fitting 101 classes × 16 images takes about 0.4 s (0.5 s with descriptions) on a 20-thread CPU.

With a CLIP embedder, class descriptions add `text_weight × 100 × cos(image, description)` to the image log-probabilities. A class with examples but no description is described by its name ("a photo of a <name>.") when the names match the examples: the name texts must classify the examples better than chance would at p < 0.05, so codes such as `K-104` or `class_3` are ignored and the task stays image-only. With 4 or more named classes that is a permutation test: the mean share of each class's examples that go to its own name, against the names handed round the classes at random. A class's examples mostly go to the same name together, whatever it means, so counting each example as a separate trial (a binomial test) passed meaningless names 15–19% of the time with 5–10 classes of 4 tight-clustered images; this passes about 5%. With fewer, which can't be tested that way (3 classes have only 6 orders), it is a one-sided binomial test over the examples. Then each name is checked on its own (its examples must rank among the images most similar to it), so in a task that mixes real names with codes only the real names are used: with a share of the classes' names replaced by codes, the coded classes now lose 2 points on average where they lost 30 (on Food-101 with a fifth of the names real, 72% → 23% at 2 examples per class). A class left without text in a task where others have it has its text scores mapped onto the real texts' scale, so it no longer draws images away from the described classes (half the classes described: 51.4% → 61.3% at 1 example per class, 85.7% → 87.3% at 16). Chance allows for unbalanced classes: names that send every image to the largest class do no better than always guessing it. In the binomial test it is estimated from where the texts send every example, described classes' too, so a single class without a description can still be described by its name. Evaluation decides this again in each cross-validation fold from that fold's training examples alone, so a held-out example never helps decide whether names are used. On the six benchmark datasets with PE Core B/16 and no descriptions, this takes 1 example per class from 56.1% to 75.6% and 16 from 87.3% to 88.4%, while meaningless names cost at most 0.3 points. Turn it off with `fewshot config TASK --no-names` or in Settings. A class can then work from its description alone, and a task with no images at all is plain CLIP zero-shot. Combining text and images at the logit level, rather than averaging their vectors, is what makes adding images improve accuracy instead of diluting the text signal. Text-only classes still get an image-side anchor by shifting their text vector across CLIP's modality gap.

`reject_below` returns "unknown" when an image's similarity to its predicted class falls below a threshold (that class's nearest example, or its prototype; usually the best similarity, though a description can tip the prediction to a class the image is a little less similar to). Use similarity for this, not confidence: softmax confidence can be 1.00 for an image of a class the task doesn't contain. The Evaluate tab (and `fewshot eval`) suggests a value that a new image of a class reaches with probability at least 95%, judging by the correct held-out predictions (a conformal bound: the k-th lowest of their n similarities, k = ⌊0.05 (n + 1)⌋, or the lowest below 19 of them), and shows a histogram of held-out similarities where you can pick another. Zero-shot tasks compare images with text, which scores far lower (about 0.2–0.35 for CLIP), so they use a separate `reject_below_zero_shot`. With a threshold set, a prediction's `labels` lists every class whose own similarity reaches it, best first (multi-label). A task with a single class predicts that class for everything, so with a threshold it tells members from outsiders (one-class or anomaly detection).

Classes differ in how tightly their images cluster, so a class can have its own threshold, which overrides `reject_below` for predictions of that class and decides whether that class is listed in another prediction's `labels` (even one whose own top class was rejected). Evaluation suggests one per class with at least 5 correct held-out predictions (again for 95% of new images; with under 19 of them, the lowest similarity, which keeps n/(n+1)); apply them from the Evaluate tab's per-class table, with `fewshot eval --apply-class-thresholds`, or one at a time with `fewshot class threshold TASK CLASS 0.82` (`--clear` goes back to the task's). Through the API: `PUT .../class-thresholds` with `{"thresholds": {"cat": 0.82, "dog": null}}`. Zero-shot predictions keep using `reject_below_zero_shot`.

A class description can hold several prompts, one per line (`fewshot class describe` and the UI's template accept several); their embeddings are averaged. The `flip` setting averages each image's embedding with its mirror image's, which usually helps a little when left and right don't matter. Predictions can list the labelled examples most like each image as evidence (`?evidence=3`, `predict --evidence 3`; the Predict tab shows them), which helps spot a mislabelled example behind a wrong answer. Confidence can be calibrated: evaluation fits a temperature so that a confidence of 0.9 means right about 90% of the time and reports the calibration error before and after (with at least 50 scored examples); it is suggested (`calibration.temperature_helps` in the API and `eval --json`) only if it lowers the error by more than 0.005, the same in the UI and the CLI. Apply it from the Evaluate tab or with `config --temperature`. Predictions don't change, only their confidence. Changing the classifier, its parameters, the text weight or names-as-text clears it, since it calibrated the old confidences. With CLIP and the prototype classifier, uncalibrated confidence is usually far too low. Evaluation reports accuracy, macro-F1, top-2/3/5 accuracy, per-class recall and precision, a confusion matrix with row totals (click a cell in the UI to list its examples, right or wrong) and every held-out prediction (`fewshot eval --csv`, or Export in the UI). Its `warnings` say what makes the numbers misleading: a task with a single class can be evaluated, but every example is predicted as that class, so its accuracy is always 1.0 and what the evaluation tells is the suggested reject threshold, for one-class detection (`fewshot eval` prints the warning and the Evaluate tab shows it). Leave-one-out for the prototype and kNN classifiers is computed in closed form instead of refitting per example, for tasks without descriptions whose names aren't candidates for text (with names-as-text on, each fold decides whether to use the names, so those tasks refit too). "Find near-duplicate examples" on the Evaluate tab (`fewshot dupes`) lists pairs of examples that look almost the same; pairs with different labels are usually labelling mistakes, and the UI offers to give both the same label.

Images are embedded as 8-bit RGB. Transparent pixels (an alpha channel, or a PNG's transparent palette entry or colour) become white. Grayscale with more than 8 bits (16-bit PNG and TIFF, 32-bit and float TIFF) is scaled with 0 as black and, as white, the value the file says is white: a TIFF's MaxSampleValue tag (or a BitsPerSample under 16), or 65535 for a PNG with an sBIT chunk, which by the PNG standard means its samples fill all 16 bits. Most files don't say, and 10- to 14-bit data from medical and industrial cameras is usually stored in 16 bits as it is, so dividing by 257 as a browser does would leave it nearly black; instead each image's 99.9th percentile is white, like an automatic exposure (or ImageJ's auto contrast). Every image is then well exposed, as the embedders (trained on photos) expect, and a few hot pixels don't change the result, but absolute brightness isn't kept across images: to compare a 12-bit camera's images by brightness, set MaxSampleValue to 4095 when writing them. Floats from 0 to 2 are read as 0–1 (anything over 1 clipped), other floats like integers, and images with negative values are stretched between their 0.1st and 99.9th percentiles. Colour images with 16 bits per channel are read as Pillow reads them, by the top 8 bits of each value (as a browser does), so 10- to 14-bit colour stored in 16 bits comes out dark: only grayscale is rescaled. Pass a 16-bit PNG as a file or its bytes rather than an opened PIL image from bytes, or its sBIT chunk can't be read.

## Measured accuracy

Accuracy over every class of six datasets at once (Oxford Pets, DTD textures, Oxford Flowers, FGVC Aircraft, EuroSAT, Food-101; 10 to 102 classes), with k example images per class, 3 random draws, up to 50 test images per class, the `gda` classifier, and a description per class such as "a photo of a {}, a type of pet." (averaged over the six datasets):

| Embedder | 0 | 1 | 2 | 4 | 8 | 16 examples per class |
|---|---|---|---|---|---|---|
| PE Core L/14, 336 px (most accurate preset) | 80.3% | 83.5% | 86.7% | 88.9% | 91.1% | 92.4% |
| SigLIP 2 L/16, 256 px | 77.7% | 81.3% | 84.4% | 87.1% | 89.3% | 91.0% |
| PE Core B/16 (default) | 75.5% | 78.6% | 81.8% | 84.5% | 87.0% | 88.7% |
| SigLIP 2 B/16, 256 px | 73.0% | 76.8% | 80.4% | 83.7% | 86.8% | 88.6% |
| CLIP ViT-B/32 LAION-2B (previous default) | 60.5% | 66.9% | 69.9% | 74.4% | 77.5% | 79.8% |

Images only, without descriptions:

| Embedder | 1 | 2 | 4 | 8 | 16 |
|---|---|---|---|---|---|
| PE Core L/14, 336 px | 64.3% | 78.9% | 85.6% | 89.5% | 91.7% |
| PE Core B/16 | 56.1% | 70.0% | 78.9% | 84.3% | 87.3% |
| DINOv2 ViT-L/14 | 60.0% | 67.9% | 74.8% | 80.7% | 85.2% |
| DINOv3 ViT-B/16 | 50.9% | 63.9% | 73.4% | 80.3% | 84.1% |
| DINOv2 ViT-S/14 | 54.6% | 65.3% | 72.5% | 79.2% | 83.5% |
| CLIP ViT-B/32 | 48.0% | 60.4% | 69.3% | 75.6% | 78.9% |

On these datasets the text-capable models beat DINOv2 and DINOv3 even on images alone, so prefer PE Core whether or not your classes have meaningful names; DINOv2 may still suit images unlike web photos (try both with "Compare models"). Descriptions help most at few examples (zero-shot PE Core B/16 is 75.5%); naming the kind of thing ("…, a type of flower") is worth about 2 points over "a photo of a {}" at 0–1 examples, while generic prompt ensembles did not help. Averaging each image with its mirror image (`flip`) added under a point, and combining two models' predictions (PE Core L with SigLIP 2 L) about one point at twice the embedding cost. Embedding speed on an RTX 5070: about 300 images/s for the B/16 models, 70 for PE Core L/14-336. Run the same protocol on your own folder of `<class>/<image>` with `fewshot bench <folder> --way 0 --query 50 --episodes 3 --shots 1 --shots 16 --embedder ... [--text-template ...]` (`--way 0` uses every class; the default is 5-way episodes).

To choose a model for your own task, compare embedders on its labelled examples: "Compare models" on the Evaluate tab, `fewshot compare TASK -e timm:vit_small_patch14_dinov2.lvd142m` (or `--presets` for all of them), or `POST .../compare/jobs` with `{"embedders": [...]}` (a background job, like evaluation). Each model is cross-validated with the task's other settings, and the results give accuracy, macro-F1 and the time taken (images already in the embedding cache are fast, so the first run of a model is slower). A model that can't be loaded is reported and the others still run. Switch with "Use this model" or `fewshot config TASK --embedder ...`; nothing changes until you do. Switching clears the temperature and reject thresholds (the task's and each class's), which were fitted to the old model's scores; evaluate again for new suggestions, or undo the switch to get them back. Changing only thresholds keeps the last evaluation current, since evaluation doesn't depend on them.

## CLI

```bash
fewshot -h                                    # commands by topic; every command takes -h, with examples
fewshot create pets --embedder openclip:PE-Core-B-16@meta
fewshot import pets ./photos --shots 5        # ./photos/<class>/<image>; skips .ipynb_checkpoints, __MACOSX...
fewshot add pets Beagle a.jpg b.jpg           # a new class name close to an existing one needs --new-class
fewshot class describe pets "a photo of a {}, a type of pet"
fewshot class ls pets                         # classes, counts, thresholds, descriptions; also --json
fewshot class rename pets Beagle beagle       # relabels its examples; also: class add/rm/threshold
fewshot eval pets                             # leave-one-out cross-validation; --csv for every prediction
fewshot eval pets --apply-class-thresholds    # also set each class's suggested reject threshold
fewshot compare pets --presets                # cross-validate the task with every preset embedder
fewshot predict pets new/ https://example.com/cat.jpg --json   # also --csv
fewshot predict pets --from-file list.txt --jsonl  # a JSON line per image, printed 256 images at a time
fewshot predict pets new/ --revision 41       # with an earlier version of the task (one kept for undo)
fewshot watch pets ./incoming --out ./sorted  # sort new images into ./sorted/<class>/ as they arrive
fewshot config pets --classifier knn --param k=3 --reject-below 0.7 --flip   # --param adds to the params
fewshot example ls pets --label Beagle        # also: add, rm, relabel, tag --add/--remove, note
fewshot dupes pets                            # near-duplicate examples
fewshot undo pets
fewshot rename pets dogs-and-cats
fewshot export pets pets.zip && fewshot import-task pets.zip --name pets-copy
fewshot export pets - | ssh gpu-box fewshot import-task -   # '-' is stdout and stdin
fewshot list --json                           # also show, class ls, example ls, eval, bench, cache info, gc --json
fewshot bench ./photos --embedder timm:vit_small_patch14_dinov2.lvd142m --shots 1 --shots 5 --seed 0 --csv
fewshot cache prune --dry-run                 # also gc --dry-run
fewshot --version                             # fewshot, torch, open_clip and Python versions, for reports
FEWSHOT_TOKEN=$(openssl rand -hex 16) fewshot serve --host 0.0.0.0
```

Results go to stdout and everything else to stderr: confirmations ("Added 12 to Beagle (3 moved from Basset_Hound), skipped 28 already in Beagle; pets now has 64 examples"), hints, warnings, progress and errors, so `fewshot dupes pets | wc -l` counts pairs and an empty result is empty output. `-q`/`--quiet` (or `FEWSHOT_QUIET=1`) hides all but results and errors, `--debug` (or `FEWSHOT_DEBUG=1`) shows tracebacks and the warnings of the libraries used, which are otherwise hidden, and `--device cpu` (or `FEWSHOT_DEVICE`) picks the device models run on; these and `--root` go before or after the command name (`fewshot --device cpu eval pets` or `fewshot eval pets --device cpu`; after it wins if both are given). A device this machine doesn't have is an error before the command does anything (status 2), naming `--device` or `FEWSHOT_DEVICE`, whichever set it; `FEWSHOT_DEVICE` alone is checked by the commands that may run a model, even when every embedding is cached. The first model load of a run is announced, with its device, and a model is loaded from the Hugging Face cache without contacting the Hub; one that isn't there yet is downloaded, and that is announced too (`HF_HUB_OFFLINE=1` refuses to, naming it). Without a terminal, runs longer than a few seconds print their progress every 10%. Long ids are shown as their first 12 characters, and any unique prefix of 4 or more is accepted.

Commands exit with status 1 when they fail (or fail for some of their inputs, such as an unreadable image), 2 when they are called wrongly (options that don't go together, a malformed or unknown `--param`) and 130 when interrupted with Ctrl-C (which says what was kept, if anything). Commands that take many images go on past the ones that fail: `predict` gives each a row with `error` set (in text, a line on stderr), and `add`, `import` and `inbox add` report and skip them (a missing file counts as one); all of them then exit 1. Images that are there already (an example of the same class, or for `inbox add` labelled or waiting already) are skipped and counted, which is not a failure unless `--strict` is given; adding or importing only such images makes no change and no undo step ("Nothing new: all 40 images are already in pets"), so re-running an import is safe. An image that is an example of another class moves. A new class is announced ("Created class Beagle in pets"), and one whose name is close to an existing class's (the same but for case, or one or two letters off) is refused as a likely typo unless `--new-class` is given, in `add`, `example relabel`, `inbox accept --label` and `import` (which then imports nothing, listing the class folders that are near misses, and otherwise names the classes it created). Errors say what to do next: a missing task's names the workspace, the tasks there and the closest name. `delete` asks before deleting (it can't be undone) and without a terminal needs `--yes`; `class rm` and `example rm` say how to undo. `ls`/`list` and `rm`/`delete` are the same command in every group. Commands that only read (`list`, `show`, `predict`...) never create the workspace, so a mistyped `--root` finds no tasks instead of making a folder (`list` says where it looked), and creating it is announced; a task whose `task.json` can't be read is skipped by `list` and reported by the others. Changes from release to release are listed in [CHANGELOG.md](CHANGELOG.md).

`serve` loads the models existing tasks use at startup (`--no-warm` skips this). With a token (`FEWSHOT_TOKEN`, or `--token`, though an option shows in the process list), the API and UI require it. It must be one nobody can guess: the server refuses to start with one shorter than 16 characters or made of fewer than 5 different characters, and a random one such as `openssl rand -hex 16` is best; the UI asks for it once, and the server answers with a session cookie that holds a signed session id, never the token: it lasts 30 days, logging out (Log out in the UI's sidebar) ends it, and changing the token ends every session. If the session ends while the UI is open, it asks for the token again over the page, keeping what it shows, and then says which uploads stopped meanwhile. Every server setting has an environment variable (`FEWSHOT_TOKEN`, `FEWSHOT_ALLOWED_HOSTS`, `FEWSHOT_MAX_UPLOAD_MB`...; see `fewshot serve --help` and `fewshot/server_settings.py`), read and checked in one place, so a bad value stops the server with a message (an empty one counts as unset); `serve` reads them the same way and its options override them, and `uvicorn fewshot.api:app` builds the same server from them, except that behind a proxy it needs uvicorn's own `--forwarded-allow-ips`. Predictions, evaluations, uploads, imports and thumbnails run on the server's own threads (`--workers`, default 4), so a burst of them queues there while everything else, and the `/healthz` check, keeps answering. `serve` refuses to listen on anything but a loopback address without a token, since anyone who can reach the port could read and change every task; `--no-token` (`FEWSHOT_ALLOW_NO_TOKEN=1`) says to do so anyway, with a warning. By default API callers can only choose preset embedders, registered ones, and ones a task already uses, so they can't make the server download arbitrary models; `--allow-any-model` lifts that. The server only answers requests addressed to an IP address or to the host names it expects (localhost, plus the machine's own name when serving on another address; add others with `--allowed-host`, or `--allowed-host '*'` for any), and refuses writes that a browser marks as coming from another site, so web pages can't reach it through DNS rebinding or cross-site requests. Example images are always served as images (`nosniff`, sandboxed). Images over 50 megapixels are refused before they are decoded (a JPEG counts at the reduced scale it is decoded at), and images are shrunk to 2048 pixels before embedding. Transparent areas are filled with white; images with transparency are embedded again once, since their cache key changed with it, so vectors cached before (made with black) aren't reused. The cache isn't keyed by device or library versions: CUDA's half precision and the CPU's full precision agree to a cosine of 0.99996. Imported zips are checked like uploads: every file must be an image whose extension matches its format, the total unpacked size is limited, and the task's embedder must pass the same model allowlist. With `--allow-urls`, API callers can send image URLs for the server to download (public addresses only, with each connection made to the address that was checked, redirects followed only to http(s) URLs, and a time limit on each whole download; the UI then shows a URL field on the Predict tab). The CLI accepts URLs in `add` and `predict` either way.

## Python

```python
from fewshot import Workspace, Pipeline
ws = Workspace("./fewshot_data")
task = ws.create("defects", embedder="timm:vit_small_patch14_dinov2.lvd142m")
task.add_example(open("ok.jpg", "rb").read(), "ok")
task.add_example(open("crack.jpg", "rb").read(), "crack")
pred = Pipeline(ws).predict(task, ["new.jpg"])[0]   # .label, .confidence, .similarity, .scores
```

To call a running server from another program, `fewshot.client.Client` covers the common operations with only the standard library: tasks, adding images, the inbox (one page, or every page with `iter_inbox`), examples (`examples`, `iter_examples`), predicting, and evaluating or comparing embedders as background jobs; `Client.request` reaches every other endpoint. `Client()` reads the server's address from `FEWSHOT_URL` (default `http://127.0.0.1:8000`) and its token from `FEWSHOT_TOKEN`; arguments override them. Images are paths, `bytes`, binary file objects, `(filename, bytes)` pairs or PIL images (sent as PNG; images without a file name are named `image-<i>`), sent at most 256 and half the server's request size limit per request and read a batch at a time, so any number works. A file that can't be read is listed in `errors`, or gets a `predict` result with `error` set and every other key empty (`None` scores), like the server's; anything else (an `int`, say) raises `TypeError` naming its index before anything is sent. Uploads are deduplicated by content, so adding them again is safe: `added` lists the new examples, `unchanged` those already there and `moved` those moved from another class. Methods return plain dicts typed as `TypedDict`s (`Prediction`, `TaskDetail`, `AddResult`, `InboxPage`, `EvalReport`...) that mirror the API's schemas, so a type checker catches `p["confidnce"]`; a newer server's extra fields are kept.

```python
from fewshot.client import Client, ConflictError
fs = Client()  # $FEWSHOT_URL and $FEWSHOT_TOKEN, or Client("http://gpu-box:8000", token="...")
try:
    fs.create_task("pets")
except ConflictError:
    pass  # it exists already
fs.add_examples("pets", "Beagle", ["a.jpg", "b.jpg"])
for p in fs.predict("pets", ["new.jpg"], top_k=3):
    print(p["file"], p["label"], p["confidence"], p["revision"])
job = fs.start_evaluate("pets")  # or fs.evaluate("pets", timeout=600), which waits
report = job.wait(on_progress=lambda j: print(j["stage"], j["done"], "/", j["total"]))
print(report["accuracy"], fs.compare("pets", ["openclip:PE-Core-B-16@meta", "timm:vit_small_patch14_dinov2.lvd142m"])["best"])
```

Every exception is a `fewshot.client.FewshotError`. An error response raises an `ApiError` subclass by status: `BadRequestError` (400), `AuthenticationError` (401), `PermissionDeniedError` (403: the server's settings refuse it, whatever the token), `NotFoundError` (404), `ConflictError` (409), `PreconditionFailedError` (412), `ValidationError` (422, with every problem in `.errors`), `RateLimitError` (429, with `.retry_after`) and `ServerError` (5xx). Each has `.status` (also `.status_code`), the stable `.code` (see [Errors](#errors)), the one-line `.detail`, the whole problem `.body` and its other members as `.fields` (`similar_to`, `revision`...); `str(e)` is `CODE: detail`. A server that can't be reached raises `APIConnectionError` (naming the URL and how to start one), one that doesn't answer within `timeout` seconds `APITimeoutError`, and a redirect, which isn't followed so the token never goes to another server, `ApiError`. A job (`start_evaluate`, `start_compare`, or `client.job(id)` to come back to one) has `.id`, `.status()`, `.wait(timeout=None, on_progress=None)`, `.cancel()` and `.result()`; one that fails raises `JobFailedError` (with the failure's `.code`), `JobCancelledError` or `JobResultExpiredError` (all `JobError`s, with `.job_id`), and `wait` past its `timeout` raises `APITimeoutError` with `.job_id`, leaving the job running. Ctrl-C while `evaluate` or `compare` waits says how to come back to the job. Methods that change a task take `if_match=REVISION` to change it only if it is still at that revision (see [Concurrent edits](#concurrent-edits)), and `add_examples` and `accept_inbox` take `new_class=True` to create a class whose name is close to an existing one's.

`task.undo()`, `task.annotate(ids, add_tags=[...], note=...)`, `task.edit_examples(ids, label=..., add_tags=[...])` and `task.edit_class(name, new_name, description)` (one undo step each), `task.add_examples_from_dir(folder, shots=5)`, `ws.rename(old, new)` and `fewshot.archive.export_task` / `import_task` do what the matching commands do. To add many images, `task.add_examples(items)` takes `(bytes, label, source)` tuples (a generator is fine) and saves `task.json` once per 256 images instead of once per image, all one undo step; consecutive calls with the same `undo_group=` are one step too (as for `task.add_to_inbox`).

To use your own model, subclass `fewshot.embedders.Embedder` (implement `dim` and `_embed_image_batch`, returning L2-normalised float32 rows) and register it under any spec string; `unregister_embedder` removes it again. Output with the wrong shape or non-finite values raises `ValueError`; rows that aren't unit length are normalised. To keep CPU preprocessing outside the per-model lock, also override `_prepare_images` (runs unlocked) and `_embed_prepared` (runs locked).

```python
from fewshot import register_embedder
register_embedder("mine:v1", MyEmbedder())
task = ws.create("parts", embedder="mine:v1")
```

## REST API

`fewshot serve` serves the API under `/api`, with interactive docs at `/docs` and the schema at `/openapi.json` (each operation has a tag, a summary and an id that is its handler's name, such as `predict`, `add_examples` or `list_tasks`, so generated clients get readable method names; errors are declared as `application/problem+json`, the routes that change a task take an optional `If-Match` header, and responses that carry a task declare their `ETag`). A first session with curl:

```bash
B=http://127.0.0.1:8000/api   # with a token, add -H "Authorization: Bearer $FEWSHOT_TOKEN" to each call
curl -s -X POST $B/tasks -H 'Content-Type: application/json' -d '{"name": "pets"}'           # 1. create a task
curl -s -X POST $B/tasks/pets/examples -F label=Beagle -F files=@beagle1.jpg -F files=@beagle2.jpg
curl -s -X POST $B/tasks/pets/examples -F label=Persian -F files=@persian1.jpg -F files=@persian2.jpg  # 2. label
curl -s -X POST "$B/tasks/pets/predict?top_k=2" -F files=@new.jpg                            # 3. predict
curl -s -i -X POST $B/tasks/pets/evaluate/jobs        # 4. start an evaluation: 202, Location: /api/jobs/<id>
curl -s $B/jobs/<id>                                 # 5. poll it until status is done; result is the report
```

### Routes

| Tag | Routes |
| --- | --- |
| tasks | `GET/POST /api/tasks`; `GET/PATCH/DELETE /api/tasks/{name}`; `POST .../rename` `{"name"}`, `.../duplicate` `{"name", "examples", "inbox"}`, `.../undo`, `.../redo`; `GET .../export` (zip; `X-Fewshot-Skipped` counts examples left out because their image was missing); `POST /api/tasks/import` (multipart `file`, optional `name` and `embedder`) |
| classes | `POST .../classes` `{"name", "description"}` (201 if new, 200 if it existed and only its description was set); `PATCH/DELETE .../classes/{label}`; `POST .../describe` `{"template"}`; `PUT .../class-thresholds` `{"thresholds": {class: value or null}}` |
| examples | `GET .../examples?offset=&limit=&label=&tag=` (one page, 100 by default, at most 1000); `POST .../examples` (multipart `label`, `files`, optional `new_class`, `undo_group`); `POST .../examples/urls` `{"label", "urls"}`; `PATCH/DELETE .../examples/{id}` (`label`, `tags`, `note`); `PATCH .../examples` `{"ids", "label", "add_tags", "remove_tags"}`; `POST .../examples/delete` `{"ids"}`; `GET .../examples/{id}/image?size=` |
| inbox | `POST .../inbox` (multipart `files`), `POST .../inbox/urls`; `GET .../inbox?sort=uncertain\|confident\|novel\|added&offset=&limit=` (one page with the model's suggestions, 100 by default, at most 1000); `POST .../inbox/accept` `{"labels": {id: class}}`, `.../inbox/accept-confident` `{"min_confidence"}`, `.../inbox/dismiss` `{"ids"}` |
| predict | `POST .../predict` (multipart `files`; `?top_k=`, `?evidence=`, `?revision=`), `POST .../predict/urls` `{"urls"}`; `GET .../duplicates?threshold=&limit=` |
| evaluate | `POST .../evaluate/jobs?folds=` and `POST .../compare/jobs` `{"embedders", "folds"}` (background jobs, below); `POST .../evaluate?folds=` answers with the report itself, which for a large task can take minutes (prefer the job) |
| jobs | `GET /api/jobs/{id}`; `DELETE /api/jobs/{id}` cancels |
| auth | `POST /api/login` `{"token"}`, `POST /api/logout` |
| system | `GET /api/health` (also `/healthz`): status, `version`, `api_version`, loaded models, running jobs, size limits; `GET /api/models` |

`...` is `/api/tasks/{name}`. In `PATCH /api/tasks/{name}` (a JSON Merge Patch), omitted fields are unchanged and `null` clears `reject_below`, `reject_below_zero_shot` or `temperature` (null for another field is a 422); `classifier_params` replaces the params, a new classifier starts with its defaults unless params are given, and a `temperature` of 1 means none, as in `fewshot config`. A rename and a new description in one `PATCH .../classes/{label}` are one undo step, as are a move and new tags of examples; `PATCH .../examples` and `.../examples/delete` change nothing if any id is unknown. A prediction carries the `revision` of the task that made it; one for a file that can't be read has `error` set, `label`, `top_label`, `confidence` and `similarity` null and `scores` empty, so it can't pass for a real score. `?revision=N` predicts with an earlier version still kept for undo. Evaluation reports give each held-out prediction's `source` (the image's file name), and duplicate pairs their `sources`, as `fewshot eval --json` and `dupes --json` do.

Uploads are deduplicated by content hash, so sending one again is safe: an upload answers 201 if it stored anything new, 200 if every image was there already, and 400 `NO_IMAGES_ADDED` if it could add nothing (no image could be read or, for the inbox, every readable one is an example already), with each file and why in `errors` (`[{file, error}]`, as in a successful upload); `added` lists the new examples, `unchanged` those already examples of that class, `moved` (`{id, previous_label}`) those that were examples of another class and moved, `errors` each file that couldn't be used, and `created_classes` the class the upload created. A label is checked as the CLI checks it: a new class whose name is close to an existing class's (the same but for case, or one or two letters off, such as `beagle` or `Beagel` for `Beagle`) is refused with 422 `CLASS_NAME_NEAR_MISS` (`similar_to` names the class, `pointer` the field) unless the request sends `new_class=true`; this holds for uploads, `.../examples/urls`, relabelling one or several examples and accepting inbox images. A name that is new and not close to any class creates the class, and every route that can create one says so in `created_classes`: uploads, and relabelling or accepting inbox images, which answer the task with it. Example and inbox uploads take an optional form field `undo_group`, any string of at most 64 characters the client chooses: consecutive uploads to a task with the same value, with no other change to it in between, are one undo step, described as a whole ("add 250 examples to red, blue"). The group is noted with the undo step on disk, so it holds across server processes; `fewshot.client` and the web UI send one for each upload they split into several requests.

Each uploaded image is limited to 50 MB (`FEWSHOT_MAX_UPLOAD_MB`), a whole upload request to 1024 MB (`FEWSHOT_MAX_REQUEST_MB`, refused with 413 before the body is stored) and to 1000 files, the bodies that list ids (`PATCH .../examples`, `.../examples/delete`, `.../inbox/accept`, `.../inbox/accept-confident`, `.../inbox/dismiss`) to 16 MB, enough for about 350,000 ids, and any other request body to 1 MB. The limit comes from the route: only a multipart body sent to an upload route (`.../examples`, `.../inbox`, `.../predict`, `/api/tasks/import`) may be large, whatever another request's `Content-Type` claims. Uploads are read a few images at a time as they are stored or classified, not all at once. Example and inbox uploads (`POST .../examples`, `POST .../inbox`) take an optional form field `undo_group`, any string of at most 64 characters the client chooses: consecutive uploads to a task with the same value, with no other change to it in between, are one undo step, described as a whole ("add 250 examples to red, blue"). The group is noted with the undo step on disk, so it holds across server processes; `fewshot.client` and the web UI send one for each upload they split into several requests. A class description holds at most 10,000 characters and 64 prompts. `GET /api/health` also reports the size limits, so clients can batch below them.

### Background jobs

Evaluating a large task, or comparing embedders on it, runs as a background job. `POST .../evaluate/jobs` (`?folds=N`, at least 2; default leave-one-out up to 100 examples, 300 for prototype and kNN, then 10- or 5-fold) and `POST .../compare/jobs` (`{"embedders": [...], "folds": N}`, at most 8 embedders, each passing the same allowlist as a task's embedder) answer 202 with the job, `Location: /api/jobs/{id}` and `Retry-After: 1`. A task that can't be evaluated is refused at once, with the same error as without a job (400 `NO_EXAMPLES`). `GET /api/jobs/{id}` reports `status` (`running`, `cancelling`, `done`, `failed`, `cancelled`; while running it also sends `Retry-After`), `stage` (`embedding` counts images, `evaluating` counts folds; a comparison's are like `2/3 embedding`), `done`/`total`, and once done the report as `result` (only the last 10 finished jobs keep theirs; older ones say `expired`). A failed job has `error` (one line) and `problem`, the error as an error response would give it, with its `code`. `DELETE /api/jobs/{id}` cancels a job at its next progress step; until it stops it counts towards the limit of 4 jobs running or being cancelled at once (429 `TOO_MANY_JOBS`, with `Retry-After`, beyond that), and `/api/health` reports it in `jobs_cancelling`. Starting an evaluation that is already running returns that job. Jobs live in the server's memory, so after a restart their ids are unknown (404 `JOB_NOT_FOUND`, saying so). So do logged-out sessions and the counts of wrong tokens: the server is one process (with `--workers` threads for heavy work), and running several processes of it (`uvicorn fewshot.api:app --workers N`, gunicorn, `WEB_CONCURRENCY`) isn't supported, since each would know only its own jobs and logouts; a server started that way logs a warning. The web UI uses jobs to show progress and a Cancel button.

### Errors

Every error, the framework's (unknown route, wrong method, a body that doesn't parse) included, is an RFC 9457 problem, sent as `application/problem+json`:

```json
{"type": "urn:fewshot:problem:class-name-near-miss", "title": "Class name close to an existing class's",
 "status": 422, "code": "CLASS_NAME_NEAR_MISS", "instance": "/api/tasks/pets/examples",
 "detail": "No class 'beagle' in pets; did you mean 'Beagle'? Send new_class=true to create it",
 "task": "pets", "label": "beagle", "similar_to": ["Beagle"], "pointer": "/label"}
```

`code` is stable and meant for programs; `detail` is one line for people and may change. `type` is `urn:fewshot:problem:` and the code in kebab case: a name to dispatch on, not a link (the codes are listed below), or `about:blank` for an unknown route, a method a route doesn't take, or a 500. Members such as `task`, `label`, `example_id`, `job_id`, `revision`, `limit_bytes`, `similar_to` (the closest existing names, as for a missing task or class) and `pointer` are present when they apply. A request that doesn't validate (422 `VALIDATION_FAILED`) lists every problem at once in `errors`, each with a JSON `pointer` into the body (`/text_weight`) or the query or path `parameter`, a `detail` naming the value received and the rule (`text_weight must be greater than or equal to 0; got -5`) and a `code`; `detail` sums them up. The input itself isn't sent back. A body that isn't valid JSON is a 422 too, saying where it stopped parsing (`the body isn't valid JSON (at character 8): Expecting value`, with an empty `pointer`). Unknown body fields and unknown query parameters (`?topk=` for `?top_k=`) are 422s too, never silently ignored, and filtering examples by a class the task doesn't have is a 404 `CLASS_NOT_FOUND` naming the closest, not an empty page.

Statuses follow one policy: 422 when a request field is invalid (its type, range or choices), 400 when the request is well-formed but can't be done (no image was readable, a bad class name), 401 for a missing or wrong token, 403 when the server's settings refuse it, 404 for a missing task, class, example, job or route, 409 when it conflicts with the task as it is (a name taken, nothing to undo), 412 when `If-Match` names a revision the task has moved on from, 413 for a body over its limit, 415 for an upload route sent something other than `multipart/form-data`, or a JSON route sent a body that isn't `application/json` (such as a form, or `curl -d` without `-H 'content-type: application/json'`), 429 (with `Retry-After`) for too many wrong tokens or jobs, and 500 for a bug (logged; the body only says so). The codes:

| Status | Codes |
| --- | --- |
| 400 | `INVALID_REQUEST`, `INVALID_EMBEDDER`, `UNKNOWN_CLASSIFIER`, `NO_IMAGES_ADDED`, `NO_EXAMPLES`, `UPLOAD_INTERRUPTED`, `UNKNOWN_HOST` |
| 401 | `NOT_SIGNED_IN` (no token or session), `WRONG_TOKEN` |
| 403 | `EMBEDDER_NOT_ALLOWED`, `URL_FETCH_DISABLED`, `CROSS_SITE`, `NO_SERVER_TOKEN` |
| 404 | `TASK_NOT_FOUND`, `TASK_UNREADABLE`, `CLASS_NOT_FOUND`, `EXAMPLE_NOT_FOUND`, `REVISION_NOT_FOUND`, `JOB_NOT_FOUND`, `NOT_FOUND`, `ROUTE_NOT_FOUND` |
| 405 | `METHOD_NOT_ALLOWED` |
| 409 | `TASK_EXISTS`, `CLASS_EXISTS`, `NOTHING_TO_UNDO`, `NOTHING_TO_REDO` |
| 412 | `PRECONDITION_FAILED` |
| 413 | `PAYLOAD_TOO_LARGE` |
| 415 | `UNSUPPORTED_MEDIA_TYPE` |
| 422 | `VALIDATION_FAILED`, `CLASS_NAME_NEAR_MISS` |
| 429 | `TOO_MANY_WRONG_TOKENS`, `TOO_MANY_JOBS` |
| 500 | `INTERNAL` |

### Concurrent edits

Every response carrying a task (`GET`, and every change) sends `ETag: "<revision>"`. Send it back as `If-Match` on a change (any route that changes a task, its classes, examples or inbox) to make it only if the task is still at that revision: otherwise the answer is 412 `PRECONDITION_FAILED` with the current `revision`, and nothing changes. The revision is compared under the task's write lock, together with the change, so of several changes sent at once with the same `If-Match` exactly one is made and the others get 412. Without `If-Match` a change is made whatever the revision, so this is opt-in.

### Versions and compatibility

`/api/health` reports the server's `version` and its `api_version` (now `1`), every response carries `X-Fewshot-Version`, and `/openapi.json` gives the version too. Within an `api_version`, responses only gain fields: clients must ignore fields they don't know (`fewshot.client` keeps them). A field or parameter to be removed is first marked deprecated in the OpenAPI schema (and answered with a `Deprecation: true` header when a request uses it) and kept for at least one minor release; changes that can break a client are listed in [CHANGELOG.md](CHANGELOG.md).

### Access, limits and proxies

When the server was started with a token, send it as `Authorization: Bearer <token>`, or `POST /api/login` with `{"token": ...}` to get a session cookie (`HttpOnly`, `SameSite=Strict`, and `Secure` over HTTPS); `POST /api/logout` ends the session. After 10 wrong tokens within a minute from one address (at login or as Bearer headers), further wrong ones from it get 429 (`TOO_MANY_WRONG_TOKENS`, with `Retry-After`) until it has sent none for a minute. The right token is always accepted (compared in constant time), so a stranger guessing from a shared address can't lock out the clients there that know it; that a right guess would get in too is no weakness, since the token is too long to guess. Behind a reverse proxy, every client has the proxy's address unless the server trusts the proxy's `X-Forwarded-For`: set `--forwarded-allow-ips` (`FEWSHOT_FORWARDED_ALLOW_IPS`, default 127.0.0.1, so a proxy on the same machine is trusted; CIDR ranges work) to the proxy's address. A server with a token that receives forwarded requests from a proxy it doesn't trust logs a warning saying so. URL downloads share a budget per request: the request size limit in total and 2 minutes in all, 4 at a time. `serve --max-upload-mb/--max-request-mb` set the size limits. `POST /api/tasks/import` also takes an `embedder` field to import with another model; the export's `X-Fewshot-Skipped` header counts examples left out because their image was missing. `/api/health` and `/api/login` need no token. A server without a token answers only requests that reach it on a loopback address (127.0.0.1, ::1) and come from this machine: anything arriving on another interface or a Unix socket, or carrying a proxy's forwarding headers (`X-Forwarded-For`, `Forwarded`, `X-Forwarded-Host`, `X-Real-IP`, which a proxy on this machine adds for clients anywhere), gets 403 saying so (except `/healthz`), however it was started, unless `FEWSHOT_ALLOW_NO_TOKEN=1` says to serve other machines without one. Served under a path prefix (`uvicorn --root-path`), these checks and the token's apply to the prefixed paths just the same. Writes whose `Origin` (or Sec-Fetch-Site) shows another site are refused (403), and so are reads of `/api` that the browser marks as sent from another site, except example images; `/api` answers are `Cache-Control: no-store`, images `private` and immutable, and the UI's pages carry a Content-Security-Policy that also forbids framing them.

## Deploying

`fewshot predict` streams: with `--jsonl` or `--csv` each batch of 256 images is printed as soon as it is classified, and a `--from-file` list (`-` for stdin) is read as it arrives, so a long one can be piped through (a listed file that can't be read gets an error row instead of stopping the run), and every prediction records the task `revision` that made it. `fewshot watch TASK FOLDER --out OUT` classifies images as they land in FOLDER (once a file's size has stopped changing) and moves each into `OUT/<class>/`, `OUT/_unknown/` (rejected, or below `--min-confidence`) or `OUT/_error/` (an unreadable file is retried for 30 seconds after it last changed, in case it is still arriving), appending a JSON line per image to `OUT/predictions.jsonl`; files are never overwritten, `--copy` leaves the originals, `--once` handles what is there and stops, and the task is re-read each time, so labelling more examples improves the sorting while it runs (a task without examples yet is waited for; any other error, such as a model that can't be loaded, stops it with exit status 1).

The Dockerfile builds the web UI and a server image (CPU PyTorch by default):

```bash
export FEWSHOT_TOKEN=$(openssl rand -hex 16)
docker compose up -d                      # http://localhost:8000 (this machine only); sign in with the token
docker build --build-arg TORCH_INDEX=https://download.pytorch.org/whl/cu128 -t fewshot:gpu .   # NVIDIA
docker run --gpus all -p 8000:8000 -e FEWSHOT_TOKEN -v fewshot-data:/data -v fewshot-models:/models fewshot:gpu
```

Tasks, images and the embedding cache live in the `/data` volume and downloaded model weights in `/models`, so both survive rebuilds. `docker-compose.yml` publishes the port on 127.0.0.1 only, for a reverse proxy with HTTPS on the same machine (publish `8000:8000` to reach it from others); it trusts no proxy's `X-Forwarded-For`, since such a proxy connects from Docker's gateway address, as every other process on the machine does, and anything trusted could claim any client address: wrong tokens are then counted for all clients behind the proxy at once (the right token always works); to count them per client, set `FEWSHOT_FORWARDED_ALLOW_IPS` to a proxy container's own address. Inside, the server listens on all interfaces, so set `FEWSHOT_TOKEN`: without one the container stops at once, and `docker logs` says why, unless `FEWSHOT_ALLOW_NO_TOKEN=1`. Set `FEWSHOT_ALLOWED_HOSTS` (comma-separated) to the host names clients use: by default the server answers requests by IP address and for localhost and the container's own name only. It runs as an unprivileged user (compose also makes the container read-only but for the volumes and a 2 GB `/tmp` tmpfs, where uploads are spooled while they are stored (exports over 64 MB spill into `/data`), and drops all capabilities) and its health check polls `/healthz`; over HTTPS the login cookie is `Secure`.

The reverse proxy must pass on the browser's `Host` header (or send it as `X-Forwarded-Host`): the server refuses writes whose `Origin` matches neither (403, naming both), and nginx's `proxy_pass` sends `Host: 127.0.0.1:8000` unless told otherwise. Add the public name to `FEWSHOT_ALLOWED_HOSTS` too. For nginx:

```nginx
server {
    listen 443 ssl;
    server_name fewshot.example.com;
    # ssl_certificate ...; ssl_certificate_key ...;
    client_max_body_size 1024m;        # the server enforces its own limits (FEWSHOT_MAX_REQUEST_MB)
    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_request_buffering off;   # stream uploads instead of spooling them first
        proxy_read_timeout 600s;       # a large upload or evaluation can take minutes
    }
}
```

Caddy passes all of these on by default: `fewshot.example.com { reverse_proxy 127.0.0.1:8000 }`.

## Tests and checks

`scripts/check.sh` runs everything CI runs (`.github/workflows/ci.yml`):

| Check | Requirement |
|---|---|
| `ruff check .` | no findings |
| `mypy` | `--strict` on `fewshot`; relaxed annotations for `tests` |
| `pylint fewshot tests` | 10.00/10 |
| `pytest --cov` | 100% line and branch coverage (`fail_under = 100`) |
| `npm run typecheck` / `lint` / `build` in `web/` | `tsc`, ESLint (typescript-eslint strict type-checked) and Stylelint with zero warnings |
| `npm test` / `npm run check:api` in `web/` | the UI's unit tests (Vitest) pass; `src/api-schema.ts` matches the server's OpenAPI schema |

The Python tests take about 30 seconds and download no models: they use fake embedders registered with `register_embedder`, and mock open_clip, timm and CUDA. They are grouped by topic (`tests/test_<topic>.py`, e.g. `test_fetch`, `test_archive`, `test_history`, `test_auth`), with shared fixtures and helpers in `tests/conftest.py`; a test that leaves anything in the working directory fails. One opt-in test embeds an image and a text with the smallest real preset: `FEWSHOT_TEST_MODELS=1 pytest -m model` (it downloads the weights into `HF_HOME` unless they are cached). Besides these checks, CI runs the locking, transaction, history and store tests on macOS, and builds the Docker image, starts it and checks that `/healthz` answers and `/` serves the UI. A weekly workflow (`.github/workflows/scheduled.yml`) runs the checks against the newest release of every dependency, and the real-model test.

### Dependencies

`pyproject.toml` gives loose ranges, as a library should (with lower bounds where the code needs them: open_clip 3.0 for the PE Core presets). `constraints.txt` pins the exact versions of every dependency, and theirs, that the checks pass with; CI and the Dockerfile install with `-c constraints.txt`, so a new upstream release can't break them, and the weekly workflow shows when one would. torch is pinned without its local label (`torch==2.11.0` matches `2.11.0+cpu` and `+cu128`) and installed with `--no-deps` from the wheel index of your choice. To refresh the pins: in a fresh environment, install without the constraints (`pip install --no-deps torch torchvision --index-url ...`, then `pip install -e ".[dev,siglip]"`), run `scripts/check.sh`, and then `python scripts/freeze_constraints.py > constraints.txt`.
