# fewshot

[![CI](https://github.com/forrest-grover/fewshot/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/forrest-grover/fewshot/actions/workflows/ci.yml) [![coverage](https://img.shields.io/endpoint?url=https://raw.githubusercontent.com/forrest-grover/fewshot/badges/coverage.json)](https://github.com/forrest-grover/fewshot/actions/workflows/ci.yml)

Few-shot image classification from a handful of labeled examples per class. Images are embedded with a pretrained vision model (CLIP or DINOv2) and classified against the class examples, so there is no training run: adding, removing, or relabeling an example changes predictions immediately.

The same engine is exposed four ways: a Python library, a CLI, a REST API, and a web UI.

## Setup

```bash
conda create -p ./.env python=3.12 nodejs=22 -c conda-forge
./.env/bin/pip install --no-deps -c constraints.txt torch torchvision --index-url https://download.pytorch.org/whl/cu128   # RTX 50xx needs cu128+
./.env/bin/pip install -c constraints.txt -e ".[dev]"
cd web && npm install && npm run build && cd ..
./.env/bin/fewshot serve            # UI at http://127.0.0.1:8000, API docs at /docs
```

Data lives in `$FEWSHOT_HOME` (default `./fewshot_data`): one folder per task with its images and `task.json`, plus a shared SQLite embedding cache. The server and CLI can use the same workspace at once: each change to a task locks it, starts from the latest saved `task.json`, and replaces the file atomically (the lock needs Linux or macOS), and the cache runs in WAL mode so one process's writes don't fail the other's. `fewshot cache info` shows the cache's size per model; `fewshot cache prune` deletes vectors no task's examples use, such as those of deleted examples and `bench` datasets (with every task locked meanwhile, so an image being added can't lose its vector; the cache reuses the space, and `--vacuum` shrinks the file, which keeps other processes from writing to the cache while it runs). At most two built-in models stay loaded at once (`FEWSHOT_MAX_MODELS`); loading another unloads the least recently used. The web UI scales images down to at most 1024 px on the longest side (as JPEG) before uploading them as examples or for prediction, and sends a large drop in batches of up to 100 images (and at most 32 MB, or half the server's request size limit if that is lower), showing progress with a Cancel button; an upload keeps going while you switch tabs, stops when you open another task, and if it stops part-way the UI says how many images got in; the CLI and API store whatever they are given. In the UI you can drag thumbnails between classes, tick several (Shift+click for a range) to move or delete them together, and paste images: on the Examples tab into the class under the pointer, on the Predict tab to classify them. Number keys 1–9 move ticked examples to that class, or add the highlighted prediction as that class (Enter accepts the prediction). Prediction and evaluation results stay while you switch tabs. The home page is a dashboard of all tasks: size, inbox, the last evaluation's accuracy (marked * when the task changed since) and warnings such as classes with too few examples or strong imbalance; `fewshot list` shows the same. On the Examples tab you can search file names, tags and notes, sort, and collapse classes; clicking a thumbnail opens it full size, where ←/→ step through the class, 1–9 move the example and Delete removes it. Press ? for every keyboard shortcut. A task can be duplicated (Settings, `fewshot copy`, `POST .../duplicate`), with or without its examples, to try other settings safely. For UI development, run `fewshot serve` and `npm run dev` in `web/`; Vite proxies `/api` to port 8000. `npm test` runs the UI's unit tests, and after changing the API, `npm run gen:api` regenerates the UI's types from its OpenAPI schema (`npm run check:api` checks they are current).

Every change to a task can be undone (`fewshot undo`, the Undo button or Ctrl+Z in the UI, `POST .../undo`) and redone until the next change (`fewshot redo`, Ctrl+Shift+Z, `POST .../redo`); each step is labelled, e.g. "delete 3 examples". The last 20 versions of `task.json` are kept in the task's `history/` folder, and a deleted example's image stays until no kept version names it, and `cache prune` keeps the vectors of images undo or redo may bring back. A damaged `cache.sqlite` is moved aside and a new cache started. Images are stored once per workspace, in `blobs/`, and hard-linked into each task that uses them; `fewshot cache prune` also removes stored images no task uses, and `fewshot gc` cleans up after crashes: half-made or half-deleted task folders, image files no version of their task uses, and unused stored images. Creating, importing and deleting a task move whole folders into place, so a crash never leaves half a task, and a task whose folder was renamed (by hand, or by a rename that was interrupted) opens under the folder's name. One undo takes back a whole upload or import, however large (a drop of more than 100 images in the UI is sent as several uploads with the same `undo_group` form field, which makes them one undo step too). Exports lock the task while they run. Examples can carry tags and a note (`fewshot example tag/note`, or in the UI the ✎ button on a thumbnail, or tick several and "Tag…", which open a small editor with suggestions from the task's tags), and the Examples tab can show only one tag. After an undo or redo the UI says what it was and offers the reverse. On a phone, the task list folds into a menu. A task can be renamed, and exported as a zip of its settings, labels and images and imported into another workspace (`fewshot export` / `fewshot import-task`, or Settings → Export and New task → Import).

Models run on CUDA if available, then Apple's GPU (MPS), then the CPU; `FEWSHOT_DEVICE` (e.g. `cpu`, `cuda:1`) picks one. If the GPU runs out of memory, the batch is split in halves; later batches stay smaller until 20 have fitted, then grow back. A model is never unloaded to make room for another while an operation that uses it (embedding, predicting, evaluating) is still running, even between batches. The SigLIP 2 preset needs `transformers` for its tokenizer (`pip install -e ".[siglip]"`).

## Inbox: labelling with the model's help

Each task has an inbox for images that aren't labelled yet (the Inbox tab, `fewshot inbox add TASK dir/`, `POST .../inbox`). The model suggests a class for each, and the inbox can be ordered so that the images it is least sure about come first (labelling those teaches it the most), the most confident come first (to accept them in bulk), or the least familiar come first (new kinds of image). On the Inbox tab, Enter accepts the highlighted suggestion, 1–9 label it as that class and Delete dismisses it; "Accept N suggestions" labels everything above a confidence. From the command line: `fewshot inbox ls TASK --sort uncertain`, `fewshot inbox accept TASK --min-confidence 0.9`, `fewshot inbox accept TASK ID... --label cat`, `fewshot inbox dismiss TASK ID...`. Labelling moves images to the examples; every step can be undone, and the inbox is part of exports.

## How classification works

Each task has an embedder, a classifier, and classes. A class has example images, an optional text description, or both.

| Classifier | Image score |
|---|---|
| `gda` (default) | Gaussian discriminant analysis: class means (pulled towards their descriptions) with a shared covariance shrunk towards a sphere, on centred features; its weight against the text and its confidence scale are fitted per task |
| `prototype` | cosine similarity to the class's mean embedding |
| `knn` | similarity-weighted vote of the k nearest examples |
| `logreg` | logistic regression trained on the examples |

`gda` shrinks its covariance by D/(D + dof) (D: embedding size, dof: images minus classes), so with one image per class it is a nearest-mean classifier and with many it uses how each class actually spreads. With descriptions, each class's mean is also pulled towards its description moved across the modality gap, as if the description were λ more images: a few images are a noisy estimate of where a class lies, and the description a biased but steady one. λ is set per task by empirical Bayes (1.5 × σ²/τ², from how far the images spread around their class means and how far the means sit from their descriptions; after DEFTS, arXiv 2611.21993), so it is large when images are few or scattered and fades as they accumulate. The pull is skipped when the descriptions don't pick out their own classes' images (each class's mean must be nearest its own description more often than chance, by a one-sided binomial test at p < 0.05; with fewer than 4 described classes, where that test can't pass, the descriptions must instead classify the example images better than chance, which on pairs of classes adds 0.3 points at 4 images per class): with shuffled descriptions it would cut held-out accuracy at 2 images per class from 28.6% to 22.6% with PE Core B/16, and from 45.5% to 22.2% with PE Core L/14. On the held-out datasets this adds 0.5/1.1/0.9/0.5/0.1 points at 1/2/4/8/16 images per class with PE Core B/16 (0.2/0.8/0.6/0.4/0.2 with PE Core L/14), and makes confidence better calibrated on average, mostly at 2 images per class; image-only tasks are unchanged. The image term's weight against `100 × cos` is then chosen by leave-one-out cross-entropy on the examples, pulled towards 0.2·k^0.6 for k images per class (fully at k = 1, less as k grows), since how much to trust the images over the text differs a lot between tasks: flowers want five times the weight pets do; `text_weight` multiplies the text's share on top of that, in the scores and in the means' pull towards the descriptions (1 keeps the tuned balance, 2 doubles the text's weight, and values near 0 fit almost as without text). A last scale, fitted the same way with each example also taken out of the covariance, makes confidence match accuracy. Over six datasets (Pets, DTD and Flowers to develop it; Aircraft, EuroSAT and Food-101 held out) with CLIP ViT-B/32 and SigLIP 2, it beats `prototype` at every shot count; on the held-out datasets with descriptions, 1/2/4/8/16 shots go from 61.6/64.7/66.8/67.7/68.2% to 61.6/65.7/70.6/75.1/78.1%, and image-only from 45.1/55.0/63.6/68.9/71.7% to 46.6/58.4/67.5/73.8/77.6% (all classes of each dataset at once, 3 seeds). Fitting 101 classes × 16 images takes about 0.2 s.

With a CLIP embedder, class descriptions add `text_weight × 100 × cos(image, description)` to the image log-probabilities. A class with examples but no description is described by its name ("a photo of a <name>.") when the names match the examples: the name texts must classify the examples better than chance would, by a one-sided binomial test at p < 0.05, so codes such as `K-104` or `class_3` are ignored and the task stays image-only. Chance allows for unbalanced classes: names that send every image to the largest class do no better than always guessing it. It is estimated from where the texts send every example, described classes' too, so a single class without a description can still be described by its name. Evaluation decides this again in each cross-validation fold from that fold's training examples alone, so a held-out example never helps decide whether names are used. On the six benchmark datasets with PE Core B/16 and no descriptions, this takes 1 example per class from 56.1% to 75.8% and 16 from 87.3% to 88.4%, while meaningless names cost at most 0.2 points. Turn it off with `fewshot config TASK --no-names` or in Settings. A class can then work from its description alone, and a task with no images at all is plain CLIP zero-shot. Combining text and images at the logit level, rather than averaging their vectors, is what makes adding images improve accuracy instead of diluting the text signal. Text-only classes still get an image-side anchor by shifting their text vector across CLIP's modality gap.

`reject_below` returns "unknown" when an image's best similarity falls below a threshold. Use similarity for this, not confidence: softmax confidence can be 1.00 for an image of a class the task doesn't contain. The Evaluate tab (and `fewshot eval`) suggests a value that keeps 95% of correct held-out predictions, and shows a histogram of held-out similarities where you can pick another. Zero-shot tasks compare images with text, which scores far lower (about 0.2–0.35 for CLIP), so they use a separate `reject_below_zero_shot`. With a threshold set, a prediction's `labels` lists every class whose own similarity reaches it, best first (multi-label). A task with a single class predicts that class for everything, so with a threshold it tells members from outsiders (one-class or anomaly detection).

Classes differ in how tightly their images cluster, so a class can have its own threshold, which overrides `reject_below` for predictions of that class and decides whether that class is listed in another prediction's `labels` (even one whose own top class was rejected). Evaluation suggests one per class with at least 5 correct held-out predictions (again keeping 95% of them); apply them from the Evaluate tab's per-class table, with `fewshot eval --apply-class-thresholds`, or one at a time with `fewshot class threshold TASK CLASS 0.82` (`--clear` goes back to the task's). Through the API: `PUT .../class-thresholds` with `{"thresholds": {"cat": 0.82, "dog": null}}`. Zero-shot predictions keep using `reject_below_zero_shot`.

A class description can hold several prompts, one per line (`fewshot class describe` and the UI's template accept several); their embeddings are averaged. The `flip` setting averages each image's embedding with its mirror image's, which usually helps a little when left and right don't matter. Predictions can list the labelled examples most like each image as evidence (`?evidence=3`, `predict --evidence 3`; the Predict tab shows them), which helps spot a mislabelled example behind a wrong answer. Confidence can be calibrated: evaluation fits a temperature so that a confidence of 0.9 means right about 90% of the time and reports the calibration error before and after (with at least 50 scored examples); apply it from the Evaluate tab or with `config --temperature`. Predictions don't change, only their confidence. Changing the classifier, its parameters, the text weight or names-as-text clears it, since it calibrated the old confidences. With CLIP and the prototype classifier, uncalibrated confidence is usually far too low. Evaluation reports accuracy, macro-F1, top-2/3/5 accuracy, per-class recall and precision, a confusion matrix with row totals (click a cell in the UI to list its examples, right or wrong) and every held-out prediction (`fewshot eval --csv`, or Export in the UI). Leave-one-out for the prototype and kNN classifiers is computed in closed form instead of refitting per example, for tasks without descriptions whose names aren't candidates for text (with names-as-text on, each fold decides whether to use the names, so those tasks refit too). "Find near-duplicate examples" on the Evaluate tab (`fewshot dupes`) lists pairs of examples that look almost the same; pairs with different labels are usually labelling mistakes, and the UI offers to give both the same label.

Images are embedded as 8-bit RGB. Transparent pixels (an alpha channel, or a PNG's transparent palette entry or colour) become white. Grayscale with more than 8 bits (16-bit PNG and TIFF, 32-bit and float TIFF) is scaled with 0 as black and, as white, the value the file says is white: a TIFF's MaxSampleValue tag (or a BitsPerSample under 16), or 65535 for a PNG with an sBIT chunk, which by the PNG standard means its samples fill all 16 bits. Most files don't say, and 10- to 14-bit data from medical and industrial cameras is usually stored in 16 bits as it is, so dividing by 257 as a browser does would leave it nearly black; instead each image's 99.9th percentile is white, like an automatic exposure (or ImageJ's auto contrast). Every image is then well exposed, as the embedders (trained on photos) expect, and a few hot pixels don't change the result, but absolute brightness isn't kept across images: to compare a 12-bit camera's images by brightness, set MaxSampleValue to 4095 when writing them. Floats from 0 to 2 are read as 0–1 (anything over 1 clipped), other floats like integers, and images with negative values are stretched between their 0.1st and 99.9th percentiles.

## Measured accuracy

Accuracy over every class of six datasets at once (Oxford Pets, DTD textures, Oxford Flowers, FGVC Aircraft, EuroSAT, Food-101; 10 to 102 classes), with k example images per class, 3 random draws, up to 50 test images per class, the `gda` classifier, and a description per class such as "a photo of a {}, a type of pet." (averaged over the six datasets):

| Embedder | 0 | 1 | 2 | 4 | 8 | 16 examples per class |
|---|---|---|---|---|---|---|
| PE Core L/14, 336 px (most accurate preset) | 80.3% | 83.5% | 86.7% | 88.9% | 91.1% | 92.4% |
| SigLIP 2 L/16, 256 px | 77.7% | 81.3% | 84.4% | 87.1% | 89.3% | 91.0% |
| PE Core B/16 (default) | 75.5% | 78.6% | 81.8% | 84.5% | 87.0% | 88.7% |
| SigLIP 2 B/16, 256 px | 73.0% | 76.8% | 80.4% | 83.7% | 86.8% | 88.6% |
| CLIP ViT-B/32 LAION-2B (previous default) | 60.5% | 66.9% | 69.9% | 74.4% | 77.5% | 79.8% |

Images only, without descriptions:

| Embedder | 1 | 2 | 4 | 8 | 16 |
|---|---|---|---|---|---|
| PE Core L/14, 336 px | 64.3% | 78.9% | 85.6% | 89.5% | 91.7% |
| PE Core B/16 | 56.1% | 70.0% | 78.9% | 84.3% | 87.3% |
| DINOv2 ViT-L/14 | 60.0% | 67.9% | 74.8% | 80.7% | 85.2% |
| DINOv3 ViT-B/16 | 50.9% | 63.9% | 73.4% | 80.3% | 84.1% |
| DINOv2 ViT-S/14 | 54.6% | 65.3% | 72.5% | 79.2% | 83.5% |
| CLIP ViT-B/32 | 48.0% | 60.4% | 69.3% | 75.6% | 78.9% |

On these datasets the text-capable models beat DINOv2 and DINOv3 even on images alone, so prefer PE Core whether or not your classes have meaningful names; DINOv2 may still suit images unlike web photos (try both with "Compare models"). Descriptions help most at few examples (zero-shot PE Core B/16 is 75.5%); naming the kind of thing ("…, a type of flower") is worth about 2 points over "a photo of a {}" at 0–1 examples, while generic prompt ensembles did not help. Averaging each image with its mirror image (`flip`) added under a point, and combining two models' predictions (PE Core L with SigLIP 2 L) about one point at twice the embedding cost. Embedding speed on an RTX 5070: about 300 images/s for the B/16 models, 70 for PE Core L/14-336. Run the same protocol on your own folder of `<class>/<image>` with `fewshot bench <folder> --way 0 --query 50 --episodes 3 --shot 1 --shot 16 --embedder ... [--text-template ...]` (`--way 0` uses every class; the default is 5-way episodes).

To choose a model for your own task, compare embedders on its labelled examples: "Compare models" on the Evaluate tab, `fewshot compare TASK -e timm:vit_small_patch14_dinov2.lvd142m` (or `--presets` for all of them), or `POST .../compare/jobs` with `{"embedders": [...]}` (a background job, like evaluation). Each model is cross-validated with the task's other settings, and the results give accuracy, macro-F1 and the time taken (images already in the embedding cache are fast, so the first run of a model is slower). A model that can't be loaded is reported and the others still run. Switch with "Use this model" or `fewshot config TASK --embedder ...`; nothing changes until you do. Switching clears the temperature and reject thresholds (the task's and each class's), which were fitted to the old model's scores; evaluate again for new suggestions, or undo the switch to get them back. Changing only thresholds keeps the last evaluation current, since evaluation doesn't depend on them.

## CLI

```bash
fewshot create pets --embedder openclip:PE-Core-B-16@meta
fewshot import pets ./photos --shots 5        # ./photos/<class>/<image>; skips .ipynb_checkpoints, __MACOSX...
fewshot add pets Beagle a.jpg b.jpg
fewshot class describe pets "a photo of a {}, a type of pet"
fewshot class rename pets Beagle beagle       # relabels its examples; also: class add/rm/threshold
fewshot eval pets                             # leave-one-out cross-validation; --csv for every prediction
fewshot eval pets --apply-class-thresholds    # also set each class's suggested reject threshold
fewshot compare pets --presets                # cross-validate the task with every preset embedder
fewshot predict pets new/ https://example.com/cat.jpg --json   # also --csv
fewshot predict pets --from-file list.txt --jsonl  # a JSON line per image, printed 256 images at a time
fewshot predict pets new/ --revision 41       # with an earlier version of the task (one kept for undo)
fewshot watch pets ./incoming --out ./sorted  # sort new images into ./sorted/<class>/ as they arrive
fewshot config pets --classifier knn --param k=3 --reject-below 0.7 --flip   # --param adds to the params
fewshot example ls pets --label Beagle        # also: rm, relabel, tag --add/--remove, note
fewshot dupes pets                            # near-duplicate examples
fewshot undo pets
fewshot rename pets dogs-and-cats
fewshot export pets pets.zip && fewshot import-task pets.zip --name pets-copy
fewshot list --json                           # also show --json, models --json
fewshot bench ./photos --embedder timm:vit_small_patch14_dinov2.lvd142m --shot 1 --shot 5
fewshot cache prune --dry-run
FEWSHOT_TOKEN=$(openssl rand -hex 16) fewshot serve --host 0.0.0.0
```

Commands exit with status 1 when they fail (or fail for some of their inputs, such as an unreadable image) and 2 when they are called wrongly (options that don't go together, a malformed `--param`). Commands that only read (`list`, `show`, `predict`...) never create the workspace, so a mistyped `--root` finds no tasks instead of making a folder; a task whose `task.json` can't be read is skipped by `list` and reported by the others.

`serve` loads the models existing tasks use at startup (`--no-warm` skips this). With a token (`FEWSHOT_TOKEN`, or `--token`, though an option shows in the process list), the API and UI require it. It must be one nobody can guess: the server refuses to start with one shorter than 16 characters or made of fewer than 5 different characters, and a random one such as `openssl rand -hex 16` is best; the UI asks for it once, and the server answers with a session cookie that holds a signed session id, never the token: it lasts 30 days, logging out ends it, and changing the token ends every session. Every server setting has an environment variable (`FEWSHOT_TOKEN`, `FEWSHOT_ALLOWED_HOSTS`, `FEWSHOT_MAX_UPLOAD_MB`...; see `fewshot serve --help` and `fewshot/server_settings.py`), read and checked in one place, so a bad value stops the server with a message (an empty one counts as unset); `serve` reads them the same way and its options override them, and `uvicorn fewshot.api:app` builds the same server from them, except that behind a proxy it needs uvicorn's own `--forwarded-allow-ips`. Predictions, evaluations, uploads, imports and thumbnails run on the server's own threads (`--workers`, default 4), so a burst of them queues there while everything else, and the `/healthz` check, keeps answering. `serve` refuses to listen on anything but a loopback address without a token, since anyone who can reach the port could read and change every task; `--no-token` (`FEWSHOT_ALLOW_NO_TOKEN=1`) says to do so anyway, with a warning. By default API callers can only choose preset embedders, registered ones, and ones a task already uses, so they can't make the server download arbitrary models; `--allow-any-model` lifts that. The server only answers requests addressed to an IP address or to the host names it expects (localhost, plus the machine's own name when serving on another address; add others with `--allowed-host`, or `--allowed-host '*'` for any), and refuses writes that a browser marks as coming from another site, so web pages can't reach it through DNS rebinding or cross-site requests. Example images are always served as images (`nosniff`, sandboxed). Images over 50 megapixels are refused before they are decoded (a JPEG counts at the reduced scale it is decoded at), and images are shrunk to 2048 pixels before embedding. Transparent areas are filled with white; vectors cached before this change (made with black) are reused for those same images. Imported zips are checked like uploads: every file must be an image whose extension matches its format, the total unpacked size is limited, and the task's embedder must pass the same model allowlist. With `--allow-urls`, API callers can send image URLs for the server to download (public addresses only, with each connection made to the address that was checked, redirects followed only to http(s) URLs, and a time limit on each whole download; the UI then shows a URL field on the Predict tab). The CLI accepts URLs in `add` and `predict` either way.

## Python

```python
from fewshot import Workspace, Pipeline
ws = Workspace("./fewshot_data")
task = ws.create("defects", embedder="timm:vit_small_patch14_dinov2.lvd142m")
task.add_example(open("ok.jpg", "rb").read(), "ok")
task.add_example(open("crack.jpg", "rb").read(), "crack")
pred = Pipeline(ws).predict(task, ["new.jpg"])[0]   # .label, .confidence, .similarity, .scores
```

To call a running server from another program, `fewshot.client.Client` covers the common operations (tasks, adding images, the inbox, predicting, evaluating as a background job) with only the standard library, and `Client.request` reaches every other endpoint. Images are paths or `(filename, bytes)` pairs, sent at most 256 and half the server's request size limit per request and read a batch at a time, so any number works; errors raise `ApiError` with the HTTP status and the server's message (status 0 when the connection fails):

```python
from fewshot.client import Client
fs = Client("http://gpu-box:8000", token="...")
fs.add_examples("pets", "Beagle", ["a.jpg", "b.jpg"])
for p in fs.predict("pets", ["new.jpg"], top_k=3):
    print(p["file"], p["label"], p["confidence"], p["revision"])
```

`task.undo()`, `task.annotate(ids, add_tags=[...], note=...)`, `task.edit_examples(ids, label=..., add_tags=[...])` and `task.edit_class(name, new_name, description)` (one undo step each), `task.add_examples_from_dir(folder, shots=5)`, `ws.rename(old, new)` and `fewshot.archive.export_task` / `import_task` do what the matching commands do. To add many images, `task.add_examples(items)` takes `(bytes, label, source)` tuples (a generator is fine) and saves `task.json` once per 256 images instead of once per image, all one undo step; consecutive calls with the same `undo_group=` are one step too (as for `task.add_to_inbox`).

To use your own model, subclass `fewshot.embedders.Embedder` (implement `dim` and `_embed_image_batch`, returning L2-normalised float32 rows) and register it under any spec string; `unregister_embedder` removes it again. Output with the wrong shape or non-finite values raises `ValueError`; rows that aren't unit length are normalised. To keep CPU preprocessing outside the per-model lock, also override `_prepare_images` (runs unlocked) and `_embed_prepared` (runs locked).

```python
from fewshot import register_embedder
register_embedder("mine:v1", MyEmbedder())
task = ws.create("parts", embedder="mine:v1")
```

## REST API

`GET/POST /api/tasks`, `GET/PATCH/DELETE /api/tasks/{name}` (in `PATCH`, `classifier_params` replaces the params, a new classifier starts with its defaults unless params are given, and a `temperature` of 1 means none, as in `fewshot config`), `POST /api/tasks/{name}/classes`, `PATCH/DELETE .../classes/{label}` (a rename and a new description in one `PATCH` are one undo step, as are a move and new tags of examples), `POST .../describe`, `POST .../examples` (multipart `label` + `files`), `PATCH/DELETE .../examples/{id}`, `PATCH .../examples` (`{"ids": [...], "label": ...}` moves several) and `POST .../examples/delete` (`{"ids": [...]}`), both changing nothing if any id is unknown, `GET .../examples/{id}/image` (`?size=N` returns a JPEG scaled down to fit N×N pixels, 16–2048), `POST .../predict` (multipart `files`, optional `?top_k=N`, `?evidence=N` and `?revision=N` to use an earlier version still kept for undo; each prediction carries the `revision` that made it, and an unreadable file gets an `error` field instead of a label), `POST .../evaluate`, `GET /api/health` (also `/healthz`). Also: `GET .../examples?offset=&limit=&label=&tag=` (one page of examples), `PATCH .../examples/{id}` with `tags` and `note`, `PATCH .../examples` with `add_tags`/`remove_tags`, `POST .../undo`, `POST .../rename` (`{"name": ...}`), `GET .../export` (zip) and `POST /api/tasks/import` (multipart `file`, optional `name`), `GET .../duplicates?threshold=0.95`, the inbox (`POST .../inbox` with files, `POST .../inbox/urls`, `GET .../inbox?sort=uncertain|confident|novel|added`, `POST .../inbox/accept` with `{"labels": {id: class}}`, `POST .../inbox/accept-confident` with `{"min_confidence": 0.9}` to accept every suggestion that sure, `POST .../inbox/dismiss`), and, on a server started with `--allow-urls`, `POST .../predict/urls` and `POST .../examples/urls` (`{"urls": [...]}`, plus `label` to add). OpenAPI docs are served at `/docs` and the schema at `/openapi.json`; each operation id is the handler's name (`predict`, `add_examples`, `list_tasks`...), so generated clients get readable method names. Request bodies reject unknown fields (422). Each uploaded image is limited to 50 MB (`FEWSHOT_MAX_UPLOAD_MB`), a whole upload request to 1024 MB (`FEWSHOT_MAX_REQUEST_MB`, refused with 413 before the body is stored) and to 1000 files, the bodies that list ids (`PATCH .../examples`, `.../examples/delete`, `.../inbox/accept`, `.../inbox/accept-confident`, `.../inbox/dismiss`) to 16 MB, enough for about 350,000 ids, and any other request body to 1 MB. The limit comes from the route: only a multipart body sent to an upload route (`.../examples`, `.../inbox`, `.../predict`, `/api/tasks/import`) may be large, whatever another request's `Content-Type` claims. Validation errors (422) don't repeat the input they refused. Uploads are read a few images at a time as they are stored or classified, not all at once. Example and inbox uploads (`POST .../examples`, `POST .../inbox`) take an optional form field `undo_group`, any string of at most 64 characters the client chooses: consecutive uploads to a task with the same value, with no other change to it in between, are one undo step, described as a whole ("add 250 examples to red, blue"). The group is noted with the undo step on disk, so it holds across server processes; `fewshot.client` and the web UI send one for each upload they split into several requests. A class description holds at most 10,000 characters and 64 prompts. `GET /api/health` also reports the size limits, so clients can batch below them.

Evaluation of a large task can take a while, so it can also run as a background job: `POST .../evaluate/jobs` returns a job; `GET /api/jobs/{id}` reports `status` (`running`, `cancelling`, `done`, `failed`, `cancelled`), `stage` (`embedding` counts images, `evaluating` counts folds), `done`/`total`, and the report as `result` once done (only the last 10 finished jobs keep theirs; older ones say `expired`); `DELETE /api/jobs/{id}` cancels it at its next progress step; until it stops, a job being cancelled still counts towards the limit on jobs, and `/api/health` reports it in `jobs_cancelling`. Jobs live in the server's memory, so after a restart their ids are unknown (404, saying so). So do logged-out sessions and the counts of wrong tokens: the server is one process (with `--workers` threads for heavy work), and running several processes of it (`uvicorn fewshot.api:app --workers N`, gunicorn, `WEB_CONCURRENCY`) isn't supported, since each would know only its own jobs and logouts; a server started that way logs a warning. The web UI uses this to show progress and a Cancel button.

When the server was started with a token, send it as `Authorization: Bearer <token>`, or `POST /api/login` with `{"token": ...}` to get a session cookie (`HttpOnly`, `SameSite=Strict`, and `Secure` over HTTPS); `POST /api/logout` ends the session. After 10 wrong tokens within a minute from one address (at login or as Bearer headers), further wrong ones from it get 429 until it has sent none for a minute. The right token is always accepted (compared in constant time), so a stranger guessing from a shared address can't lock out the clients there that know it; that a right guess would get in too is no weakness, since the token is too long to guess. Behind a reverse proxy, every client has the proxy's address unless the server trusts the proxy's `X-Forwarded-For`: set `--forwarded-allow-ips` (`FEWSHOT_FORWARDED_ALLOW_IPS`, default 127.0.0.1, so a proxy on the same machine is trusted; CIDR ranges work) to the proxy's address. A server with a token that receives forwarded requests from a proxy it doesn't trust logs a warning saying so. At most 4 background jobs run or are being cancelled at once (429 beyond that), and starting an evaluation that is already running returns that job. URL downloads share a budget per request: the request size limit in total and 2 minutes in all, 4 at a time. `serve --max-upload-mb/--max-request-mb` set the size limits. `POST /api/tasks/import` also takes an `embedder` field to import with another model; the export's `X-Fewshot-Skipped` header counts examples left out because their image was missing. `/api/health` and `/api/login` need no token. A server without a token answers only requests that reach it on a loopback address (127.0.0.1, ::1): anything arriving on another interface gets 403 saying so (except `/healthz`), however it was started, unless `FEWSHOT_ALLOW_NO_TOKEN=1` says to serve other machines without one. Writes whose `Origin` (or Sec-Fetch-Site) shows another site are refused (403), and so are reads of `/api` that the browser marks as sent from another site, except example images; `/api` answers are `Cache-Control: no-store`, images `private` and immutable, and the UI's pages carry a Content-Security-Policy that also forbids framing them.

## Deploying

`fewshot predict` streams: with `--jsonl` or `--csv` each batch of 256 images is printed as soon as it is classified, and a `--from-file` list (`-` for stdin) is read as it arrives, so a long one can be piped through (a listed file that can't be read gets an error row instead of stopping the run), and every prediction records the task `revision` that made it. `fewshot watch TASK FOLDER --out OUT` classifies images as they land in FOLDER (once a file's size has stopped changing) and moves each into `OUT/<class>/`, `OUT/_unknown/` (rejected, or below `--min-confidence`) or `OUT/_error/` (an unreadable file is retried for 30 seconds after it last changed, in case it is still arriving), appending a JSON line per image to `OUT/predictions.jsonl`; files are never overwritten, `--copy` leaves the originals, `--once` handles what is there and stops, and the task is re-read each time, so labelling more examples improves the sorting while it runs (a task without examples yet is waited for).

The Dockerfile builds the web UI and a server image (CPU PyTorch by default):

```bash
export FEWSHOT_TOKEN=$(openssl rand -hex 16)
docker compose up -d                      # http://localhost:8000 (this machine only); sign in with the token
docker build --build-arg TORCH_INDEX=https://download.pytorch.org/whl/cu128 -t fewshot:gpu .   # NVIDIA
docker run --gpus all -p 8000:8000 -e FEWSHOT_TOKEN -v fewshot-data:/data -v fewshot-models:/models fewshot:gpu
```

Tasks, images and the embedding cache live in the `/data` volume and downloaded model weights in `/models`, so both survive rebuilds. `docker-compose.yml` publishes the port on 127.0.0.1 only, for a reverse proxy with HTTPS on the same machine (publish `8000:8000` to reach it from others); it trusts `X-Forwarded-For` from Docker's gateway addresses (`FEWSHOT_FORWARDED_ALLOW_IPS`, default `172.16.0.0/12` there), where such a proxy connects from, so limits on wrong tokens apply per client; set it to the proxy's own address if other containers can reach this one. Inside, the server listens on all interfaces, so set `FEWSHOT_TOKEN`: without one it refuses every request from outside the container (403, saying why; only `/healthz` answers), unless `FEWSHOT_ALLOW_NO_TOKEN=1`. Set `FEWSHOT_ALLOWED_HOSTS` (comma-separated) to the host names clients use: by default the server answers requests by IP address and for localhost and the container's own name only. It runs as an unprivileged user (compose also makes the container read-only but for the volumes and a 2 GB `/tmp` tmpfs, where uploads are spooled while they are stored, and drops all capabilities) and its health check polls `/healthz`; over HTTPS the login cookie is `Secure`.

The reverse proxy must pass on the browser's `Host` header (or send it as `X-Forwarded-Host`): the server refuses writes whose `Origin` matches neither (403, naming both), and nginx's `proxy_pass` sends `Host: 127.0.0.1:8000` unless told otherwise. Add the public name to `FEWSHOT_ALLOWED_HOSTS` too. For nginx:

```nginx
server {
    listen 443 ssl;
    server_name fewshot.example.com;
    # ssl_certificate ...; ssl_certificate_key ...;
    client_max_body_size 1024m;        # the server enforces its own limits (FEWSHOT_MAX_REQUEST_MB)
    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_request_buffering off;   # stream uploads instead of spooling them first
        proxy_read_timeout 600s;       # a large upload or evaluation can take minutes
    }
}
```

Caddy passes all of these on by default: `fewshot.example.com { reverse_proxy 127.0.0.1:8000 }`.

## Tests and checks

`scripts/check.sh` runs everything CI runs (`.github/workflows/ci.yml`):

| Check | Requirement |
|---|---|
| `ruff check .` | no findings |
| `mypy` | `--strict` on `fewshot`; relaxed annotations for `tests` |
| `pylint fewshot tests` | 10.00/10 |
| `pytest --cov` | 100% line and branch coverage (`fail_under = 100`) |
| `npm run typecheck` / `lint` / `build` in `web/` | `tsc`, ESLint (typescript-eslint strict type-checked) and Stylelint with zero warnings |
| `npm test` / `npm run check:api` in `web/` | the UI's unit tests (Vitest) pass; `src/api-schema.ts` matches the server's OpenAPI schema |

The Python tests take about 30 seconds and download no models: they use fake embedders registered with `register_embedder`, and mock open_clip, timm and CUDA. They are grouped by topic (`tests/test_<topic>.py`, e.g. `test_fetch`, `test_archive`, `test_history`, `test_auth`), with shared fixtures and helpers in `tests/conftest.py`; a test that leaves anything in the working directory fails. One opt-in test embeds an image and a text with the smallest real preset: `FEWSHOT_TEST_MODELS=1 pytest -m model` (it downloads the weights into `HF_HOME` unless they are cached). Besides these checks, CI runs the locking, transaction, history and store tests on macOS, and builds the Docker image, starts it and checks that `/healthz` answers and `/` serves the UI. A weekly workflow (`.github/workflows/scheduled.yml`) runs the checks against the newest release of every dependency, and the real-model test.

### Dependencies

`pyproject.toml` gives loose ranges, as a library should (with lower bounds where the code needs them: open_clip 3.0 for the PE Core presets). `constraints.txt` pins the exact versions of every dependency, and theirs, that the checks pass with; CI and the Dockerfile install with `-c constraints.txt`, so a new upstream release can't break them, and the weekly workflow shows when one would. torch is pinned without its local label (`torch==2.11.0` matches `2.11.0+cpu` and `+cu128`) and installed with `--no-deps` from the wheel index of your choice. To refresh the pins: in a fresh environment, install without the constraints (`pip install --no-deps torch torchvision --index-url ...`, then `pip install -e ".[dev,siglip]"`), run `scripts/check.sh`, and then `python scripts/freeze_constraints.py > constraints.txt`.
